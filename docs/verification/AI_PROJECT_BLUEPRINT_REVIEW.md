# FigureTrail — Architecture standards review

**Reviewed 24 October 2026.** Assessment of reference architecture guidelines against FigureTrail's workload, trust boundaries and verification requirements. Sources are official documentation and upstream repositories; each recommendation is evaluated for its operational purpose and limitations.

**Decision:** retain reproducible dependencies, explicit contracts, independent evaluation and correlated execution records. Reject universal architecture claims and unsupported security or evaluation guarantees. The selected design targets one local service and a bounded corpus; infrastructure is justified by workload requirements.

## Claim-by-claim assessment

| Original claim or component | Assessment and correction |
|---|---|
| “Definitive” production architecture for 2026 | Unsupported as a universal claim. A directory tree does not establish availability, security, performance or operational readiness. Document the workload, boundaries and measured acceptance evidence. |
| `.github/`, evaluation pipeline and cluster deployment workflow | Valid possible locations. A cluster/deployment workflow is unnecessary for FigureTrail's local demonstration. Separate credential-free checks from explicitly budgeted live evaluations. Protect privileged workflows from untrusted code. [GitHub Actions](https://docs.github.com/en/actions/reference/security/secure-use) |
| `copilot-instructions.md` supplies rules for Cursor/Copilot/Claude Code | Overgeneralised. GitHub documents this file for Copilot; support varies even across Copilot surfaces. Keep the existing `AGENTS.md`; verify each client's repository-instruction mechanism. [GitHub instructions](https://docs.github.com/en/copilot/concepts/prompting-and-context/custom-instructions) |
| `config/settings.yaml`, `config/prompts/`, notebooks | Reasonable optional conventions. YAML, a separate config directory and notebooks are not architectural requirements. Centralised typed settings and a versioned prompt directory suffice here. |
| `src/__init__.py` forms a “sealed production engine” | Misleading. Source layout concerns imports/packaging, not isolation. A conventional src layout is `src/<package>/`; the current flat `app/` plan is also valid. [PyPA](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/) |
| FastAPI/Litestar async routing and multiple API layers | Plausible technology options; the supplied file does not justify one over the other. Keep FastAPI and a small routing layer for FigureTrail. Asynchronous routes still require appropriate handling of blocking work. [FastAPI](https://fastapi.tiangolo.com/async/) |
| LangGraph/CrewAI state machines | Both are real frameworks, with different abstractions: LangGraph provides stateful orchestration; CrewAI distinguishes Crews and Flows. Neither is mandatory. Their suitability requires an actual orchestration need. [LangGraph](https://github.com/langchain-ai/langgraph), [CrewAI](https://github.com/crewAIInc/crewAI) |
| Mandatory provider abstraction and vector-database client | Conditional. For FigureTrail, one SDK module and SQLite/NumPy keep execution paths and dependencies explicit. Add adapters or remote storage when requirements justify them. Anthropic explicitly discusses abstraction and complexity trade-offs. [Anthropic](https://www.anthropic.com/research/building-effective-agents) |
| Vector caches described as ephemeral mocks | Inaccurate as a general description. Qdrant and Pinecone manage actual searchable indexes. Treat generated embeddings/indexes as reproducible, versioned artifacts with provenance. [Qdrant](https://github.com/qdrant/qdrant), [Pinecone](https://docs.pinecone.io/guides/get-started/overview) |
| Prompts are source assets; “never inline”; fixed directory | Versioning substantive prompts is useful. The absolute prohibition and location are policy choices, not technical necessities. A change requires appropriate regression evidence; it need not trigger an unrestricted paid run. |
| Separate variables using text/JSON formatting | Useful organisation, but formatting is not a trust boundary. Retrieved documents and tool output can carry indirect injection. Separate message roles and enforce permissions in code. [OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) |
| uv and `pyproject.toml` | Sound recommendation, not the only valid toolchain. Add the missing committed `uv.lock`, tested interpreter and locked installs. The uv toolchain and lockfile are validated in B02. [uv documentation](https://docs.astral.sh/uv/concepts/projects/layout/), [upstream repository](https://github.com/astral-sh/uv) |
| Ruff provides “zero-overhead” formatting and all structural analysis | Overstated. Ruff is a linter/formatter, not a comprehensive type checker or security audit. Pre-commit is optional; checks must also run independently in CI. [Ruff FAQ](https://docs.astral.sh/ruff/faq/), [upstream repository](https://github.com/astral-sh/ruff) |
| Pydantic runtime validation establishes type safety | Useful for boundary validation; coercion is enabled by default and strict behaviour varies by input/type. Types and schema validity do not establish correct facts, evidence or calculations. [Pydantic strict mode](https://docs.pydantic.dev/latest/concepts/strict_mode/), [structured-output limitations](https://developers.openai.com/api/docs/guides/structured-outputs) |
| Entire `data/` ignored; an “absolute local sandbox” | Incorrect as a security description. `.gitignore` affects untracked-file inclusion, not access or already tracked content. Preserve licences, provenance, manifests and permitted small fixtures; ignore generated/private subdirectories selectively. [Git](https://git-scm.com/docs/gitignore) |
| Large datasets/weights stored externally, metadata in Git | Sensible when those artifacts exist. Secure cloud buckets and fine-tuned weights are not required for this project. Small public/licensed test fixtures may be versioned deliberately. |
| Semantic firewall intercepts adversarial prompts | No such guarantee. Filters can help; least privilege, restricted tools, output validation and adversarial tests limit consequences. Inspect retrieved content as well as the initial question. [OWASP](https://genai.owasp.org/llmrisk/llm01-prompt-injection/) |
| PII engines must remove names/emails before every provider call | Too broad. Apply data minimisation and a defined sensitive-data policy. Public FinQA figures do not justify an industrial PII subsystem; secrets and any newly introduced sensitive fields still require protection. |
| Middleware token counters/circuit breakers enforce safe budgets | Incomplete. Preparation, embeddings, evaluations and agent calls may bypass HTTP middleware. Apply accounting and limits at the shared provider-call boundary. Count retries/failures, check estimated spend before calls and reconcile usage afterwards; estimates alone are not a billing guarantee. |
| `logging.json` provides structured logs/OpenTelemetry | Configuration alone does not instrument the application. Create correlated events/spans and handle export/storage. SQLite traces meet the initial scope. Current GenAI conventions now have a dedicated repository. [Instrumentation](https://opentelemetry.io/docs/languages/python/instrumentation/), [GenAI conventions](https://github.com/open-telemetry/semantic-conventions-genai) |
| Traditional exact assertions must give way to semantic evaluation | False dichotomy. Numerical results, schemas, permissions and tool arguments need deterministic checks; open-ended explanation quality can use additional reviewed or model-based scoring. [Evaluation guidance](https://developers.openai.com/api/docs/guides/evaluation-best-practices) |
| Golden dataset in `tests/evaluations/` | Valid layout option; `evals/cases/` already fulfils the role here. Missing essentials: corpus/annotation separation, document-group splits, deduplication, reserved cases, explicit units/tolerances and versioned experiment conditions. |
| Ragas/Promptfoo metrics are “deterministic indices” | Incorrect as a blanket statement. Promptfoo supports both deterministic and model-graded checks; Ragas offers LLM-based and non-LLM/ID-based recall variants. Identify the actual implementation and judge configuration. [Promptfoo assertions](https://github.com/promptfoo/promptfoo/blob/main/site/docs/configuration/expected-outputs/index.md), [Ragas recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/) |
| Faithfulness halts hallucinations; recall guarantees all needed information; relevance establishes a good answer | Overstated. Faithfulness measures consistency with supplied context, recall needs references, and relevance can coexist with numerical error. These are measurements with limits, not prevention guarantees. [Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/), [recall](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/context_recall/), [judge calibration](https://developers.openai.com/api/docs/guides/evaluation-best-practices) |

## Resulting engineering requirements

Explicit API outcomes; source-cell calculation; fixed-versus-agent comparison; corpus/index fingerprints; three retrieval/agent variants; report-group evaluation splits; positive and negative abstention checks; shared spending limits; traceable versions; and reproducible release evidence. It retains the existing architecture direction and folder names.

Release evidence consists of reproducible execution, measured comparisons, representative failures and documented trade-offs. These requirements complement the architecture and backlog; their implementation status is maintained in README and the verification reports.
